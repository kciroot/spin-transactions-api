Arquitectura: todo apunta al dominio

domain y application no importan Spring, JPA ni HTTP: reglas y flujo se prueban sin levantar el framework. El proveedor y la base de datos son puertos con adaptadores intercambiables.

Línea punteada = el adaptador implementa la interfaz del dominio (inversión de dependencias). Beneficio concreto: 19 tests del núcleo corren con solo el JDK. Costo: dos interfaces. No agregué CQRS, mensajería ni cache: sería sobre-ingeniería hoy.

Pregunta probable: ¿por qué 201 en REJECTED? Porque la transacción se creó y se registró; el resultado de negocio está en status. Es defendible, hay alternativa (200/422); abrir la conversación sobre su preferencia.

Decisión 1 · Guardar PENDING antes de llamar al proveedor

Persistir solo al final

Si el proceso muere después de que el proveedor movió dinero y antes de guardar, la operación desaparece sin rastro.

PENDING primero

Siempre queda evidencia. Una PENDING vieja o una FAILED se detecta y se concilia contra el proveedor.

Costo: un UPDATE extra por operación. Es un desvío consciente del orden del enunciado, documentado.

Esta es la decisión más importante a defender. Respuesta corta: "prefiero pagar un UPDATE a perder una transacción".

Decisión 2 · Idempotencia arbitrada por la base de datos

Cómo

  • Header Idempotency-Key + restricción UNIQUE
  • Si dos peticiones compiten, una gana y la otra recibe la transacción ganadora
  • Mismo id de transacción viaja al proveedor como Idempotency-Key

Por qué en la BD y no en memoria

  • Funciona con N réplicas sin coordinación
  • Probado con 12 hilos concurrentes sobre PostgreSQL real
  • Los reintentos del cliente no duplican dinero

Si preguntan cómo sé que el test prueba algo: el sleep amplía la carrera, el latch arranca los hilos juntos, y si quito el UNIQUE el test falla (lo comprobé: TODO verificar antes de decirlo).

Rechazo ≠ caída: resiliencia con criterio

Rechazo del proveedor

Respuesta definitiva (p. ej. saldo insuficiente). Es un valor de retorno: no se reintenta y no cuenta para el circuit breaker.

Caída / timeout / 5xx

Resultado ambiguo. Se reintenta, el breaker lo cuenta, y si falla queda FAILED para conciliar.

Retry( CircuitBreaker( HTTP ) )
timeouts: connect 1s · read 2s
retry: 3 intentos, backoff exponencial 200ms x2 con jitter
breaker: abre con >=50% fallas (>=10 llamadas), 10s abierto, 3 de prueba
perillas por variable de entorno → apagar cada mecanismo y ver la diferencia en vivo

Límite honesto: mi mock no respeta la Idempotency-Key; un proveedor real debería. Si no la soporta, max-attempts=1 y se resuelve con conciliación.

Seguridad: lo implementado y lo que corresponde al gateway

En el servicio

  • API key en tiempo constante (SHA-256 + isEqual), rotación con varias keys
  • Deny-by-default; la app no arranca sin key (fail-safe)
  • Validación estricta, consultas parametrizadas, errores sin fugas
  • Contenedor no root, FS de solo lectura, NetworkPolicy (opcional)
  • Dependabot + CI

Plataforma / siguiente paso

  • TLS y mTLS en ingress / service mesh
  • OAuth2 y rate limiting por cliente en el API gateway
  • Cifrado en reposo y de backups; usuario de BD de mínimo privilegio
  • client_id por transacción para auditoría

Por qué API key y no JWT: es servicio a servicio; JWT lo emite y valida el IdP/gateway. Migrar es cambiar un filtro en infrastructure/security sin tocar el dominio.

Operación opcional: modular y sin costo para probarla

Kubernetes (Kustomize)

  • base: Deployment (probes, graceful shutdown), Service, ConfigMap
  • componentes opt-in: autoescalado + PDB · NetworkPolicy · backup
  • overlays: local (kind, $0) · local-full · prod-example (solo referencia)

Backups en 3 capas

  • Alta disponibilidad con failover (RPO ≈ 0)
  • PITR con WAL (minutos)
  • Dump lógico verificado + restore drill make backup / make restore

Un backup no probado no existe.

Mi perfil DevOps aquí: modularidad (Kustomize components) para encender o apagar cada capacidad. Nube real: no ejecutada, solo ejemplo, por costo.
